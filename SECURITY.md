# Security review — Chapter 21

Reviewed on 16 November 2026. Source: Chapter 21 pages 19–20, which request three attacks, recorded before/fix/after results, and a `SECURITY.md` file. The baseline was commit `36b068c`. Requests used the actual Express application with an injected test user model; they did not access a teammate's database.

## Three measured findings

| Attack/check | Before | Fix | After |
| --- | --- | --- | --- |
| Request `/api/health` and inspect browser security headers | `Content-Security-Policy`, `X-Content-Type-Options`, and `Strict-Transport-Security` were absent | Helmet runs before routes; Vercel configuration also adds frontend security headers | API returns CSP, `nosniff`, and HSTS; Express identity header is absent. Covered by `server/test/security.test.js`. Frontend hosted headers still need live verification. |
| Send six wrong-password login requests from the same address | All six returned 401, with no throttle | Five failed attempts per IP per 15 minutes; successful responses are not counted | First five return 401; sixth returns JSON 429 and `Retry-After`. An additional general API limiter allows 300 requests per 15 minutes. |
| Signup with a 101-character name and otherwise valid fields | 201: the oversized name was accepted | Name length capped at 100 on input and in the schema; email capped at 254; favorite metadata also bounded | Same oversized-name request returns 400 before a database write. Operator-shaped emails also return 400. |

Example requests for a controlled local test instance:

```sh
curl -i http://localhost:3000/api/health
curl -i -X POST http://localhost:3000/api/auth/login -H "Content-Type: application/json" -d '{"email":"audit@example.test","password":"audit-password"}'
```

Repeat the second request six times with an unknown test account to observe 401 followed by 429. Do not use real credentials in recorded evidence. The oversized-name case is generated by the automated security test so its exact input and expected response remain reproducible.

## Existing protections checked

| Check | Implementation / evidence |
| --- | --- |
| Password storage | bcrypt with cost 12; passwordHash is not returned in the public user object; signup/login tests verify hash comparison. |
| Authentication | Signed, expiring JWT required on every pantry, favorites, and shopping route; missing, invalid, and expired tokens return 401. |
| Ownership / IDOR | Every private list/update/delete query includes verified userId. Bob cannot patch/delete Alice's documents; tests expect 404. |
| Mass assignment | Routes select allowed fields. Owner IDs and normalized keys come from the server, regardless of fields supplied in JSON. |
| NoSQL operator input | Query values must be strings/Booleans of the expected shape. Objects such as `{ "$ne": null }` are rejected before reaching a user query. |
| Central validation | Shared Zod schemas validate, trim, bound, and strip unknown request fields. Mongoose `sanitizeFilter` is also enabled as a defense-in-depth backstop. |
| XSS | User and recipe text is rendered as React text; no `dangerouslySetInnerHTML`. Recipe links allow HTTP/HTTPS; video links require known HTTPS YouTube hosts. Production frontend CSP is configured in `client/vercel.json`. |
| Request safety | JSON bodies limited to 16 KB; malformed JSON, oversized bodies, missing records, and upstream failures have controlled JSON errors. |
| CORS | One configured frontend origin and explicit methods/headers. JWTs are not sent on public recipe requests or to TheMealDB. |
| Secrets | Actual env files are ignored; only `.env.example` is tracked. Missing/short JWT secrets and missing MongoDB URI fail startup. No tracked `.env` paths were found in repository history during this review. |
| Production config | Production startup also fails closed when `CLIENT_ORIGIN` is missing, instead of silently allowing a development origin. |
| Client sessions | Logout and authenticated 401 clear token/profile and discard private React state. Demo storage is separate from authenticated data. |

## Verification and limits

```sh
npm --prefix server test
npm --prefix client test
```

Automated tests use injected models, so they prove request handling and ownership filters without proving a live Atlas connection or index creation. The deployed two-user check is documented in [DEPLOYMENT.md](docs/DEPLOYMENT.md); current results and verification limits are recorded in [the acceptance report](docs/ACCEPTANCE.md).

The class token-storage approach is retained: localStorage plus Bearer headers, as taught in Chapter 19 page 18. HTTPS must be supplied by the production hosts. Rate limits use an in-memory store suitable for one capstone API instance; counters reset on restart and are not shared across multiple instances. `TRUST_PROXY_HOPS=1` is set for Render so the limiter uses the client address behind that host's proxy.
